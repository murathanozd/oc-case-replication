Dated log of everything that did not work as described in the authors' tutorial, what we changed, and why.
Original scripts: `external/eventgraph_tutorial/order_process/` (pinned at `31d19b8`).

- Python 3.11.8 (project-local `.venv`); packages pinned in `requirements.txt` (neo4j 6.4.0, pandas 3.0.6, networkx 3.6.1, matplotlib 3.11.2, pm4py 2.7.23.8)

## 2026-10-05 – Step 1/2: building the event knowledge graph (`r1_neo4j/01_build_ekg.py`)

1. **Passwords differ across the authors' scripts** (`1234` in the tutorial text, `12341234` in
   `1_import_events.py`, `password` in `2_build_event_knowledge_graph.py`).
   *Change:* all R1 scripts read `NEO4J_URI`, `NEO4J_USER`, `NEO4J_PASSWORD` from the environment
   (or `.env` in the repo root, see `.env.example`).

2. **`LOAD CSV` from the repo path.** The tutorial loads the prepared CSV with an absolute `file:///` URL,
   which requires editing `neo4j.conf` (disable `server.directories.import`, allow file URLs) and
   says the path must not contain a dash; our repo path does (`oc-case-replication`).
   *Change:* `neo4j.conf` left untouched. The script copies the prepared CSV into the DBMS's own
   `import/` folder (`NEO4J_IMPORT_DIR`) and loads it as `file:///order_process_event_table_orderhandling_prepared.csv`.
   The import query is otherwise identical to the one generated by `CreateEventQuery(...)`.
   *Addition:* before wiping, the script runs `LOAD CSV ... RETURN count(*)` against the connected DBMS;
   this only succeeds if it is the DBMS whose import folder we wrote to, so the script aborts instead of
   wiping a different instance.

3. **Database wipe.** `2_build_event_knowledge_graph.py` only deletes `:Entity` nodes and relationships
   to/from events; `1_import_events.py` deletes everything. We run the latter's two delete queries
   (`queries/ekg/00_wipe.cypher`) at the start, so the whole build is re-runnable from scratch.
   The authors' partial cleanup in script 2 is therefore not run (it would be a no-op).

4. **Query storage.** The authors build queries with Python f-strings. We moved the query text into
   `r1_neo4j/queries/ekg/*.cypher` with `<<placeholder>>` markers for the f-string parts
   (entity type, attribute, property name, file name, property list). The resulting query strings are the
   same as the published ones (they are printed when the script runs).

5. **Prepared CSV is byte-identical to the authors' `prepared_logs/` file.** Our port of
   `0_prepare_log_for_import.py` (input `data/running_example/...orderhandling.csv`, which has a UTF-8 BOM
   and is identical to the authors' `input_logs/` file) produces exactly the shipped prepared file.
   Note: `logSamples.fillna(0)` in the original is a no-op (result not assigned); kept as is.

6. **Deprecation warning: `CALL { ... } IN TRANSACTIONS` without a variable scope clause.**
   Neo4j 5.26 returns `01N00 / DEPRECATION`: "CALL subquery without a variable scope clause is now
   deprecated. Use CALL () { ... }". The query runs correctly. Kept as published.

7. **`ID(e)` in the DF query.** The plan expected a deprecation warning for `ID()`; Neo4j 5.26.19 returned
   **no** notification for the DF query, also when re-checked with `EXPLAIN` (which always plans the query,
   see Step 4, item 6). Kept as published. On this data all 21 timestamps are distinct,
   so the `ID(e)` tie-breaker never decides the order of two events.

8. **Python driver version.** `requirements.txt` asks for `neo4j>=5.0`; pip installed 6.4.0.
   The authors' `session.execute_write(...)` / `session.run(...)` API is unchanged in 6.x.

## 2026-10-05 – Step 3: object relations and start/end events (`r1_neo4j/02_materialize.py`)

1. **Re-runnability without a full wipe.** A full wipe would remove the EKG built in Step 2, so this
   script instead deletes only the relationships it creates (`:REL`, `:START`, `:END`,
   `queries/materialize/00_reset.cypher`) and then runs the published queries. The full chain
   `01_build_ekg.py` → `02_materialize.py` produces byte-identical result files on repeated runs.

2. **Queries run as published:** OCPM 1 Sect. 2 (related pairs, query only) and Sect. 4.1 (`:REL`),
   OCPM 2 Sect. 2.2 (`:START`, `:END`). No changes needed.

3. **Results match the tutorial.** Sect. 2 returns 30 rows (15 undirected pairs, each in both directions),
   as in the tutorial's table. The 15 materialized `:REL` edges are exactly the 15 pairs in the
   tutorial's table of Sect. 3. No related pair has equal first timestamps, so the strict `t1 < t2`
   drops no relation on this data.

4. **One start and one end event per object.** 12 `:START` and 12 `:END` relationships; every object has
   exactly one of each, so the assumption of the paper's Def. 8 holds on the running example
   (`results/r1/start_end.csv`).

5. **Observations for later steps (not changed):**
   - The `:DF {ID:n.ID}` patterns in OCPM 2 match on the object ID only, not on `EntityType`. That is
     fine here (IDs are unique across types) but would mix objects of different types with the same ID
     in other logs (relevant for R3).
   - The query in OCPM 2 Sect. 2.5 ("traces of all objects of a specific type") uses `{ID:objId}`
     without binding `objId`, so it would fail as published. It is not part of Step 3; we will record it
     if we run it for the optional variants.
   - `:REL` only connects objects that share an event: there is no `:REL` between A and O1/O2, or between
     orders and P1 (P1 is reached only via the invoices).

## 2026-10-05 – Step 4: executions and case notions (`r1_neo4j/03_executions.py`)

1. **Queries run as published.** All queries are in `r1_neo4j/queries/executions/`. A script check
   confirmed that every file marked "verbatim" equals a code block of the tutorials (ignoring whitespace
   and comments). For each query, `results/r1/raw/<name>.json` holds the query's own output (paths, rows,
   or write counters for materializing queries) and `results/r1/<name>.json` the common format.

2. **Typo in OCPM 3.1 Sect. 3.1 (`"Order "` with trailing space).** Run as published
   (`notion_SO_Order_paths`): **0 paths, no error, no warning** – the query silently returns nothing, as no
   entity has `EntityType = "Order "`. Fixed copy (`notion_SO_Order_paths_fixed.cypher`, only change
   `"Order "` → `"Order"`): 15 paths, grouping into the 4 executions A→O1, A→O2, B→O1, B→O2. They have the
   same event sets as the executions materialized by Sect. 3.2 (`notion_SO_Order`), which has no typo.

3. **OCPM 3.1 Sect. 4.3 (Order → Invoice) has no printed query.** The text says to use
   `WITH "Order" AS startType, "Invoice" AS endType` in the queries above; `notion_Order_Invoice.cypher`
   is the Sect. 4.2 retrieval query with these two values. Marked as derived, not verbatim.

4. **Isolating materializing queries.** The tutorial materializes cumulatively (Sect. 2.3 → 3.2 → 4), and
   `MERGE` reuses existing `:Execution` nodes. We wipe only `:Execution` nodes and their relationships
   (`00_wipe_executions.cypher`) before each materializing run, so each saved result reflects that query
   alone. The retrieval queries of Sect. 4.1–4.5 run on the state left by Sect. 4, as in the tutorial.
   On this data the cumulative and isolated runs give the same executions (all Sect. 2.3/3.2 executions
   are also global ones).

5. **Common format for path queries (ours).** Sect. 3.1 returns single paths and OCPM 3.3 returns one row
   per grouping event with a list of paths; neither returns execution IDs or objects. We group paths in
   Python: Sect. 3.1 by (first, last) event; OCPM 3.3 by the query's own grouping event. The leading Order
   is the object whose `:START` (Sect. 6.2) or `:END` (Sect. 6.3) is that event; the other side is `*`,
   and `end_event` (6.2) or `start_event` (6.3) is then the list of all path ends or starts. The OCPM 3.3
   `collect(p)` contains duplicate paths, e.g. `e30` is the `:END` of I1, I2 and P1, so each path to `e30`
   appears 3 times. This does not change the event sets; we record `n_paths` and `n_distinct_paths`.

6. **Server notifications depend on the plan cache.** Neo4j only reports notifications when it plans a
   query, not when it reuses a cached plan, so a re-run can miss them. The scripts therefore record
   notifications from an `EXPLAIN` of each query. None of the Step 4 queries produces a notification
   (no deprecation, no performance warning for the unbounded `[:DF*]`).

7. **Timing.** Each query runs once untimed (warm-up: planning, page cache) and then 5 times timed
   (`results/r1/runtimes.csv`: warm-up, mean, std, and all 5 values, in ms, including result transfer to
   Python). Materializing queries are timed from a graph without `:Execution` nodes; the wipe is not timed.
   Without a warm-up the first run dominated (std larger than the mean). All queries take 1–25 ms on this
   21-event graph.

8. **Re-runnability.** Running `01_build_ekg.py` → `02_materialize.py` → `03_executions.py` again gives
   byte-identical result files (apart from `runtimes.csv`).

## 2026-10-05 – Step 5: claim check (`r1_neo4j/04_check_claims.py`)

Result: `results/r1/claims_table.md` (and `claims.json`): 14 claims, 13 *yes*, 1 *partial* (claim 14).
The script only reads the saved R1 results; the one computation outside Neo4j is a df-reachability check
on `df_edges.csv` for claim 12(b).

1. **Claim 14 (Fig. 12) is partial.** The paper writes: "Notably, the executions do not contain any invoices
   or payments as these are not involved in completing an order." The cases D[∗→O1 \ {SupplierOrder}] and
   D[∗→O2 \ {SupplierOrder}] contain no Payment events, but they do contain e18 and e5 (Create Invoice,
   correlated to the Order and to I1 / I2).
2. **Claim 13 (Fig. 11): activity name.** The paper says the cases start "in Place Order"; the activity in
   the data is "Create Order" ("Place Order" does not occur, only "Place SO").
3. **Claim 6: typo in the paper.** "each have their own invoice P1 and P2" should be I1 and I2.
4. **Def. 9 vs. the §4 query (claims 9–11).** Def. 9 allows o_st = o_end, so D[Order→Order] would also
   contain D[O1→O1] and D[O2→O2]. The paper's "single execution D[O2→O1]" and the total of 13 hold only
   because the §4 query has `nEnd <> nStart` (with self-pairs O1→O1, O2→O2, P1→P1: 16).
5. **Def. 10 vs. the OCPM 3.3 queries (claims 12–14).** Def. 10 restricts the other end to objects with a
   global start/end event; the tutorial queries accept any `:START`/`:END` event. For the unfiltered start
   case (Fig. 10) the event sets coincide (checked on `df_edges.csv`).
6. **Open point for R2 – order of filtering in Def. 11 (claims 13, 14).** It is not specified whether
   global start/end events are determined before or after removing the excluded objects' df-edges. The
   tutorial's result for D[∗→Order \ {SupplierOrder}] equals the "after" reading; the "before" reading
   would give only e1 e18 e27 e28 for ∗→O1. Not computed in Neo4j in R1.
